## Installation and configuration

The Super-SAG Windows installer includes `sag.exe`. Desktop initialization installs `super-sag.exe` and the compatible `sag.exe` in the user directory. Open a new terminal and run `super-sag --version`. Retrieval can start or reuse the local service even after the desktop closes. No standalone Super-SAG npm package has been published.

```powershell
super-sag --version
super-sag
```

The first interactive run of `super-sag` guides configuration of the JEV retrieval service. The endpoint and model prompts show their current values; press Enter to keep them. First-time setup requires a key, entered with hidden input. The default endpoint is `https://api.302ai.cn/typesafeai/v1`, and the model is `jev-latest`. CLI search needs only this retrieval configuration. The answer model is configured separately in desktop.

If no terminal was available during installation, the first terminal invocation of `super-sag` or `super-sag "search query"` opens the same setup flow. When started from a search, saving configuration resumes the original query. Existing keys automatically reuse the current configuration. Ctrl+C cancels; nothing is saved until setup finishes. Run `super-sag config` to configure it again at any time. In no-auth mode, it prompts for the endpoint and model without asking for a key.

With an existing local key file, configure it through standard input, optionally specifying the endpoint and model:

```sh
super-sag config --url "$JEV_URL" --model "$JEV_MODEL" --key-stdin < "$JEV_KEY_FILE"
```

Usually, run `super-sag` and enter the key at the hidden prompt. Do not paste keys into chat or place them in command arguments.

Keys are stored in private configuration for the current user and omitted from configuration output and installation logs. Noninteractive environments do not wait for input. An agent can read the explicit error and ask the user to run `super-sag` in a terminal. `super-sag config --if-needed` prompts only when configuration is missing and preserves existing settings. In a normal piped environment, `super-sag config` only outputs redacted configuration and whether a key exists.

Install the bundled Skill for the relevant agent under **Settings → CLI settings**, or use a command such as `super-sag install codex`. The Skill includes its companion references; verify configuration and search results. See the [development guide](/en/docs/development) for source builds.

## Sharing with desktop

CLI and the optional Super-SAG desktop use the same indexing, retrieval and configuration implementation in `core/`, along with the same user data directory, `sag.sqlite`, keys and ignore rules.

- Desktop and CLI share a standalone background service, configuration and knowledge base. Directory changes appear in both.
- The service keeps running after desktop exits. `super-sag add` returns after indexing finishes; background watching updates file and ignore-rule changes.
- `super-sag service status` shows the service version and process. `super-sag service stop` stops it; `super-sag service restart` restarts it. Status inspection does not automatically start it.
- Both modes retain access controls and directory-scope restrictions. Failures do not switch search algorithms. If CLI access was disabled, explicitly run `super-sag config --enable` to restore it.
- After installing the Super-SAG Skill for the relevant coding tool, open a new session to use it. The agent can run `super-sag add` for the current project, then `super-sag "search query"`.

## Commands

```sh
super-sag status
super-sag list
super-sag list --json
super-sag check
super-sag check /path/to/project --json
super-sag config
super-sag add
super-sag add /path/to/project --json
super-sag remove
super-sag remove /path/to/project --json
super-sag "Where are permissions checked after login?"
super-sag -c "How does configuration affect request retries?" ./src -m 5
super-sag "Where is the connection pool initialized?" --path ./server --json
super-sag -c "How are tasks cancelled?" --timeout 900 --json
super-sag -E -c '^(ERROR|WARN) [0-9]+' ./logs
super-sag -F -c 'validatePermission(' ./src --json
super-sag install claude-code
super-sag install codex
super-sag install opencode
super-sag uninstall codex
super-sag uninstall cli
```

`super-sag list` lists all knowledge-base directories, index status, file counts and indexing errors. `--json` returns a directory array. If none have been added, it returns an empty list without adding the current directory automatically.

`super-sag check` inspects the current or a specified directory. It distinguishes inclusion within an indexed directory, partial coverage of child directories, no index coverage and exclusion. It also shows index readiness, CLI access and the actual indexed-file count in the current directory. JSON `coverage` values are `included`, `partial`, `none` and `excluded`. The exit code is 0 when the directory is included, its index is ready, CLI access is enabled and indexed files exist; other check results return 1; argument or execution errors return 2. Ignore rules, directory exclusions and file types still determine searchable files. These two commands require no model configuration and do not register directories.

`super-sag status` shows only background-service connection status, service version, protocol version, process, executable, CLI access and JEV configuration status. It does not depend on the current directory's index state or start a stopped service. Use `super-sag check` for directory coverage, readiness and file counts.

`super-sag add` adds the current or a specified directory. It reuses the shared add/index workflow without creating duplicate roots. In desktop service mode, indexing runs in the background and the command returns the current state; standalone mode returns after indexing finishes. Use `super-sag check` to inspect readiness; no sync parameter is needed. `--json` returns the path, index state and current CLI availability. Added directories also appear in the desktop knowledge base.

`--types` accepts text, code and built-in documents, for example `super-sag add --types md,docx,pdf,xlsx`. Omitting it retains saved directory settings; new directories enable Markdown, text, RTF, Office, spreadsheets, EPUB and text-based PDFs by default. Scanned PDFs need a separately installed Docling; components are never downloaded automatically.

`super-sag remove` removes the current directory, a registered root or a subdirectory from the knowledge base. Roots are unregistered. Subdirectories have their indexes cleared and remain excluded from later scans and file watching. All local files remain unchanged. Running `super-sag add` for the same subdirectory restores and reindexes it. If a directory moved or its disk is offline, remove its record using the original registered absolute path. `--json` returns the removed directory path. The directory disappears immediately from desktop's knowledge base. The UI folder menu provides the same removal action; **File settings → Removed subdirectories** allows restoration.

Search requires no `search` subcommand: run `super-sag "search query"` directly. `add`, `remove`, `list`, `check`, `status`, `config`, `service`, `install` and `uninstall` are reserved management commands. Use `--` when searching those literal words or queries beginning with `-`, for example `super-sag -c -- "status"`.

Search defaults to the current working directory. A positional path and `--path` cannot be combined. The default result limit is 10 chunks, with 1–100 allowed. `-c` changes output only, without changing recall or ranking. Paths resolve relative to the command's working directory. JSON includes absolute paths, line numbers, actual ranges and truncation flags. Only `-c` returns `content`. Separate source ranges are output separately, so discontinuous chunks are not represented as continuous lines.

### Regular-expression and fixed-string matching

Without a mode option, search remains semantic. `-E` (`--extended-regexp`) uses regular expressions; `-F` (`--fixed-strings`) matches literal strings. They cannot be combined. Both run entirely locally, require no model or API key and do not trigger first-time model setup.

Both modes are case-sensitive and line-based by default. Ordinary output returns one result per matching line even if that line has multiple matches. Regular expressions use Rust regex syntax, supporting groups, alternatives, character classes and line anchors, without lookaround or backreferences. Protect shell-special characters in regular expressions with single quotes.

Matching remains restricted to registered, indexed knowledge-base directories. It respects access controls, file types, `.gitignore`, `.sagignore` and manually removed subdirectories, and reads current file contents. Results follow file traversal order. `-m` limits matching lines, `-c` displays them, and `--json` retains the same path and line-number fields. No matches produce empty results with exit code 0.

The following options require `-E` or `-F` and do not change default semantic search:

| Option | Purpose |
| --- | --- |
| `-i` / `--ignore-case` | Ignore case |
| `-w` / `--word-regexp` | Match whole words; letters, digits and underscores are word characters |
| `-x` / `--line-regexp` | Match whole lines; takes precedence over `-w` when combined |
| `-v` / `--invert-match` | Select nonmatching lines |
| `-A N` / `--after-context N` | Show N following lines |
| `-B N` / `--before-context N` | Show N preceding lines |
| `-C N` / `--context N` | Show N lines on both sides |
| `-l` / `--files-with-matches` | Output each matching filename once |
| `--count` | Count matching lines per file, including files with zero matches |
| `-o` / `--only-matching` | Show only nonempty matched substrings; multiple hits on a line are separate outputs |
| `-q` / `--quiet` | Suppress output; found = 0, not found = 1, error = 2 |
| `-e PATTERN` / `--regexp PATTERN` | Add a pattern; repeatable |
| `-f FILE` / `--file FILE` | Read patterns line by line from a UTF-8 file; `-` means standard input |
| `--include GLOB` / `--exclude GLOB` | Include or exclude filenames by glob; repeatable |

Context options automatically display content, allowing 0–1000 lines per side. Overlapping or adjacent ranges merge; JSON `matched_lines` identifies which lines matched. `-A` and `-B` override their respective sides of `-C`. File-list, count, substring and quiet output modes are mutually exclusive and cannot use context. `-o` cannot combine with `-v`; `-q` cannot combine with `--json`. `-c` always means display content; use only `--count` for counting.

`-m` limits matching lines across the entire search; ordinary output defaults to 10 lines. With `-l`, it limits matching files. `-o` returns every nonempty matching substring from selected lines. `--count` counts all matches by default. With an explicit `-m`, it stops at the global matching-line limit and does not count subsequent files. JSON `results` contains lines or substrings, and `files` contains filenames or counts, alongside `matched` and `truncated`.

Multiple `-e` and `-f` patterns use OR semantics. When these options are used, the positional argument denotes only the search directory. An empty pattern file supplies no patterns. `-e ''` matches any line, matches nothing with `-w`, and matches only empty lines with `-x`. Each pattern is limited to 2000 characters; combined patterns are limited to 16 KiB.

File filters are applied in command order, with the last matching rule taking precedence. If the first filter is `--include`, other unmatched filenames are excluded; otherwise inclusion is the default. Globs match filenames only and cannot override knowledge-base ignore rules or manual exclusions.

```sh
super-sag -F -i -w -c 'token' ./src
super-sag -E -e 'ERROR' -e 'WARN' ./logs -C 3
super-sag -F -f patterns.txt ./src --include='*.ts' --exclude='*.test.ts' -l
super-sag -F 'TODO' ./src --count
super-sag -F 'ready' ./src -q
```

The default request timeout is 600 seconds, including index checks in standalone mode. `--timeout` accepts 1–86400 seconds; large multi-batch searches may need a higher value. Ctrl+C terminates the current request with exit code 130. Search argument errors return 2, execution errors return 1, and successful or empty results return 0. `check` uses the check-specific codes above. stdout contains results; stderr contains errors, installation information and truncation notices.

Requests are limited to 32 KiB and responses to 512 KiB. At the response limit, complete chunks are retained and truncation is explicitly marked. The retrieval candidate budget is not reduced to shorten output. Changed files require a new query; the CLI does not return new line numbers for stale chunks.

## Project ignore rules

Indexing, file watching and built-in list/grep honor `.gitignore` and `.sagignore` in the project root and its subdirectories. They work without a Git repository and do not read rules outside the knowledge-base root. `.sagignore` takes precedence over `.gitignore`; deeper directories take precedence among rules of the same type.

For example, create `.sagignore` in the project root:

```text
# Exclude generated files and caches
output/
**/*.generated.md
# Exclude drafts, but retain a specific file
notes/draft-*.md
!notes/draft-final.md
```

Git ignore syntax is supported, including `*`, `**`, trailing-`/` directory rules and `!` exceptions. If a parent directory is entirely ignored, first unignore it before including its files again. Existing directory-name exclusions and manually removed subdirectories still apply; `!` cannot override them.

Standalone mode rechecks the index before the next search. With desktop auto-watching enabled, creating, modifying, deleting or renaming a rule file rechecks the project, removing newly ignored entries from the index and indexing newly included files. When watching is disabled, use reindexing in File settings. Rules do not delete or hide local files; the SAG file tree still browses them. Only manually removed subdirectories are hidden from the tree.

## Installation locations and upgrades

| Component | User-level location |
| --- | --- |
| CLI managed by desktop or installed with `super-sag install cli` | `~/.local/bin` (`super-sag.exe` and the compatible `sag.exe` on Windows) |
| Claude Code | `~/.claude/skills/super-sag/SKILL.md` |
| Codex | `~/.agents/skills/super-sag/SKILL.md` |
| OpenCode | `~/.config/opencode/skills/super-sag/SKILL.md` |



Repeating `super-sag install` updates Super-SAG-managed files. Installation records contain checksums, version and the actual CLI installation location. Later PATH-order changes do not change that location, and uninstallation follows the records. If foreign files, user modifications or altered SAG-managed terminal configuration blocks are detected, the installer stops and reports them. Uninstallation removes only verified SAG files and preserves other directory contents.

The command name is `super-sag`. On startup, the client updates managed CLIs and Super-SAG Skills not modified by the user. An explicitly uninstalled CLI is not restored automatically. The `.sagignore` filename and existing knowledge base remain unchanged.

Windows uses a separate console `sag.exe`, bundled with the application installer. Installing the CLI does not normally require administrator privileges. The Windows packaging entry point is `npm run package:windows`. Available platforms depend on the native executables actually included in a release package.

## Error handling

- Standalone mode: without a desktop service, the local core is used automatically; opening the app is unnecessary.
- Core busy: another process is using the index; retry later.
- Access disabled: enable and save CLI access in CLI settings.
- No indexed content: run `super-sag add` for the current project. The program does not search knowledge bases outside the specified directory instead.
- Index not ready: wait for indexing and inspect file-index errors.
- JEV missing or request failed: inspect configuration with `super-sag config`, or check **Settings → Model settings** in the Super-SAG desktop app.
- File changed: wait for the watcher to update, then query again.
- Installation conflict: retain existing files and establish their origin before resolving it manually.

For development and testing, `SAG_DATA_DIR` selects an isolated data directory. CLI and desktop must use the same value to share it.

## Automatic terminal configuration

- macOS/Linux support zsh, bash, fish and POSIX sh, respecting `ZDOTDIR` and `XDG_CONFIG_HOME`. Repeated installation does not duplicate configuration; uninstalling preserves existing environment settings.
- Windows updates the current user's PATH and broadcasts the environment change, without administrator privileges. Existing terminals keep their old environment; open a new terminal after installation.
- Implementation references: [zsh startup files](https://zsh.sourceforge.io/Doc/Release/Files.html), [Windows environment-change notification](https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-settingchange).
