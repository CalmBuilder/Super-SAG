## Installation and setup

The desktop app can initialize its bundled CLI; a standalone Super-SAG npm package has not been published. After initialization, run `super-sag --version` in a new terminal. See the [development guide](/en/docs/development) for source builds.

The first interactive run of `super-sag` guides configuration of the JEV retrieval service. The endpoint and model prompts show their current values; press Enter to keep them. First-time setup requires a key, entered with hidden input. The default endpoint is `https://api.302ai.cn/typesafeai/v1`, and the model is `jev-latest`. Create the API key in the [302.AI API key page](https://302.ai/api-keys/list). CLI search needs only this retrieval configuration. The answer model is configured separately in desktop.

If no terminal was available during installation, the first terminal invocation of `super-sag` or `super-sag "search query"` opens the same setup flow. When started from a search, saving configuration resumes the original query. Existing keys automatically reuse the current configuration. Ctrl+C cancels; nothing is saved until setup finishes. Run `super-sag config` to configure it again at any time.

With an existing local key file, configure it through standard input, optionally specifying the endpoint and model:

```sh
super-sag config --url "$JEV_URL" --model "$JEV_MODEL" --key-stdin < "$JEV_KEY_FILE"
```

Usually, run `super-sag` and enter the key at the hidden prompt. Do not paste keys into chat or place them in command arguments.

Keys are stored in private configuration for the current user and omitted from configuration output and installation logs. Noninteractive environments do not wait for input. An agent can read the explicit error and ask the user to run `super-sag` in a terminal. `super-sag config --if-needed` prompts only when configuration is missing and preserves existing settings. In a normal piped environment, `super-sag config` only outputs redacted configuration and whether a key exists.

Give your agent the [Super-SAG Skill GitHub link](https://github.com/CalmBuilder/Super-SAG/blob/main/cli/skills/sag/SKILL.md) and ask it to follow setup for the current project. It retrieves companion files from the same directory and completes CLI installation, Skill installation, configuration checks, project indexing and retrieval verification. The user enters the first key in a terminal. Building from source is for development; see the [development guide](/en/docs/development).

## Sharing with desktop

CLI and the optional Super-SAG desktop use the same indexing, retrieval and configuration implementation in `core/`, along with the same user data directory, `sag.sqlite`, keys and ignore rules.

Use an updated CLI to save model settings when the desktop app uses an interface language introduced in 0.3.13. A standalone 0.3.12 CLI can connect to a running 0.3.13 service. If it starts its own older service, saving settings can fail because that service does not support the saved language. Launch the updated desktop app to update its managed CLI. Update an npm-managed CLI separately.

- Desktop and CLI share a standalone background service, configuration and knowledge base. Directory changes appear in both.
- On macOS, the service keeps running after the desktop client exits, so CLI and MCP remain available. On Windows, quitting from the tray or app menu also stops the service. Reopening the desktop or running a CLI command that needs the service starts it on demand. `super-sag add` returns after indexing finishes; the running service watches file and ignore-rule changes.
- `super-sag service status` shows the service version and process. `super-sag service stop` stops it; `super-sag service restart` restarts it after the old instance has shut down and released its instance lock. Status inspection does not automatically start it.
- Both modes retain access controls and directory-scope restrictions. Failures do not switch search algorithms. If CLI access was disabled, explicitly run `super-sag config --enable` to restore it.
- After installing the Super-SAG Skill for the relevant coding tool, open a new session to use it. The agent can run `super-sag add` for the current project, then `super-sag "search query"`.

## Commands

```sh
super-sag status
super-sag list
super-sag list --json
super-sag check
super-sag check /path/to/project --json
super-sag config
super-sag add
super-sag add /path/to/project --json
super-sag remove
super-sag remove /path/to/project --json
super-sag "Where are permissions checked after login?"
super-sag -c "How does configuration affect request retries?" ./src -m 5
super-sag "Where is the connection pool initialized?" --path ./server --json
super-sag -c "How are tasks cancelled?" --timeout 900 --json
super-sag -E -c '^(ERROR|WARN) [0-9]+' ./logs
super-sag -F -c 'validatePermission(' ./src --json
super-sag install claude-code
super-sag install codex
super-sag install opencode
super-sag uninstall codex
super-sag uninstall cli
```

`super-sag list` lists all knowledge-base directories, index status, file counts and indexing errors. `--json` returns a directory array. If none have been added, it returns an empty list without adding the current directory automatically.

`super-sag check` inspects the current or a specified directory. It distinguishes inclusion within an indexed directory, partial coverage of child directories, no index coverage and exclusion. It also shows index readiness, CLI access and the actual indexed-file count in the current directory. JSON `coverage` values are `included`, `partial`, `none` and `excluded`. The exit code is 0 when the directory is included, its index is ready, CLI access is enabled and indexed files exist; other check results return 1; argument or execution errors return 2. Ignore rules, directory exclusions and file types still determine searchable files. These two commands require no model configuration and do not register directories.

`super-sag status` shows only background-service connection status, service version, protocol version, process, executable, CLI access and JEV configuration status. It does not depend on the current directory's index state or start a stopped service. Use `super-sag check` for directory coverage, readiness and file counts.

`super-sag add` adds the current or a specified directory. It reuses the shared add/index workflow without creating duplicate roots. The command waits for this indexing run; `--timeout` (default 600 seconds, for example `super-sag add --timeout 3600`) limits that wait. When the limit is reached the directory is already added, indexing continues in the background, and the message points at `super-sag list` for progress. Use `super-sag check` to inspect readiness; no sync parameter is needed. `--json` returns the path, index state and current CLI availability. Added directories also appear in the desktop knowledge base.

`--types` accepts text, code and built-in documents, for example `super-sag add --types md,docx,pdf,xlsx`. Omitting it retains saved directory settings; new directories enable Markdown, text, RTF, Office, spreadsheets, EPUB and text-based PDFs by default. Scanned PDFs can use enabled MinerU or a separately installed Docling; components are never downloaded automatically.

`super-sag remove` removes the current directory, a registered root or a subdirectory from the knowledge base. Roots are unregistered. Subdirectories have their indexes cleared and remain excluded from later scans and file watching. All local files remain unchanged. Running `super-sag add` for the same subdirectory restores and reindexes it. If a directory moved or its disk is offline, remove its record using the original registered absolute path. `--json` returns the removed directory path. The directory disappears immediately from desktop's knowledge base. The UI folder menu provides the same removal action; **File settings → Removed subdirectories** allows restoration.

Search requires no `search` subcommand: run `super-sag "search query"` directly. `add`, `remove`, `list`, `check`, `status`, `config`, `service`, `install` and `uninstall` are reserved management commands. Use `--` when searching those literal words or queries beginning with `-`, for example `super-sag -c -- "status"`.

Search defaults to the current working directory. A positional path and `--path` cannot be combined. Semantic search uses up to 10 retrieved candidates to assemble the output by default. Set `-m` to a value from 1 to 100. The per-round candidate setting can lower the number used. `-c` changes output only, without changing recall or ranking. Paths resolve relative to the command's working directory. JSON includes absolute paths, line numbers, actual ranges and truncation flags. Only `-c` returns `content`. Output is grouped by file path and heading. Overlapping or adjacent source ranges are merged, and disjoint ranges are returned separately.

### Regular-expression and fixed-string matching

Without a mode option, search remains semantic. `-E` (`--extended-regexp`) uses regular expressions; `-F` (`--fixed-strings`) matches literal strings. They cannot be combined. Both run entirely locally, require no model or API key and do not trigger first-time model setup.

Both modes are case-sensitive and line-based by default. Ordinary output returns one result per matching line even if that line has multiple matches. Regular expressions use Rust regex syntax, supporting groups, alternatives, character classes and line anchors, without lookaround or backreferences. Protect shell-special characters in regular expressions with single quotes.

Matching remains restricted to registered, indexed knowledge-base directories. It respects access controls, file types, `.gitignore`, `.sagignore` and manually removed subdirectories, and reads current file contents. Results follow file traversal order. `-m` limits matching lines, `-c` displays them, and `--json` retains the same path and line-number fields. No matches produce empty results with exit code 0.

The following text-matching options apply to `-E` or `-F` searches; `--exclude` also supports semantic search:

| Option | Purpose |
| --- | --- |
| `-i` / `--ignore-case` | Ignore case |
| `-w` / `--word-regexp` | Match whole words; letters, digits and underscores are word characters |
| `-x` / `--line-regexp` | Match whole lines; takes precedence over `-w` when combined |
| `-v` / `--invert-match` | Select nonmatching lines |
| `-A N` / `--after-context N` | Show N following lines |
| `-B N` / `--before-context N` | Show N preceding lines |
| `-C N` / `--context N` | Show N lines on both sides |
| `-l` / `--files-with-matches` | Output each matching filename once |
| `--count` | Count matching lines per file, including files with zero matches |
| `-o` / `--only-matching` | Show only nonempty matched substrings; multiple hits on a line are separate outputs |
| `-q` / `--quiet` | Suppress output; found = 0, not found = 1, error = 2 |
| `-e PATTERN` / `--regexp PATTERN` | Add a pattern; repeatable |
| `-f FILE` / `--file FILE` | Read patterns line by line from a UTF-8 file; `-` means standard input |
| `--include GLOB` / `--exclude GLOB` | Include filenames, or exclude relative paths and filenames; repeatable |

Context options automatically display content, allowing 0–1000 lines per side. Overlapping or adjacent ranges merge; JSON `matched_lines` identifies which lines matched. `-A` and `-B` override their respective sides of `-C`. File-list, count, substring and quiet output modes are mutually exclusive and cannot use context. `-o` cannot combine with `-v`; `-q` cannot combine with `--json`. `-c` always means display content; use only `--count` for counting.

`-m` limits matching lines across the entire search; ordinary output defaults to 10 lines. With `-l`, it limits matching files. `-o` returns every nonempty matching substring from selected lines. `--count` counts all matches by default. With an explicit `-m`, it stops at the global matching-line limit and does not count subsequent files. JSON `results` contains lines or substrings, and `files` contains filenames or counts, alongside `matched` and `truncated`.

Multiple `-e` and `-f` patterns use OR semantics. When these options are used, the positional argument denotes only the search directory. An empty pattern file supplies no patterns. `-e ''` matches any line, matches nothing with `-w`, and matches only empty lines with `-x`. Each pattern is limited to 2000 characters; combined patterns are limited to 16 KiB.

File filters are applied in command order, with the last matching rule taking precedence. If the first filter is `--include`, other unmatched filenames are excluded; otherwise inclusion is the default. `--include` matches filenames only; `--exclude` also supports relative paths. Neither can override knowledge-base ignore rules or manual exclusions.

```sh
super-sag -F -i -w -c 'token' ./src
super-sag -E -e 'ERROR' -e 'WARN' ./logs -C 3
super-sag -F -f patterns.txt ./src --include='*.ts' --exclude='*.test.ts' -l
super-sag -F 'TODO' ./src --count
super-sag -F 'ready' ./src -q
```

The default request timeout is 600 seconds, including index checks in standalone mode. `--timeout` accepts 1–86400 seconds and also caps how long `super-sag add` waits for indexing; reaching it ends the wait without cancelling the background index. Large multi-batch searches may need a higher value. Ctrl+C terminates the current request with exit code 130. Search argument errors return 2, execution errors return 1, and successful or empty results return 0. `check` uses the check-specific codes above. stdout contains results; stderr contains errors, installation information and truncation notices.

Requests are limited to 32 KiB and responses to 512 KiB. At the response limit, complete chunks are retained and truncation is explicitly marked. The retrieval candidate budget is not reduced to shorten output. Changed files require a new query; the CLI does not return new line numbers for stale chunks.

## Project ignore rules

Indexing, file watching and built-in list/grep honor `.gitignore` and `.sagignore` in the project root and its subdirectories. They work without a Git repository and do not read rules outside the knowledge-base root. `.sagignore` takes precedence over `.gitignore`; deeper directories take precedence among rules of the same type.

For example, create `.sagignore` in the project root:

```text
# Exclude generated files and caches
output/
**/*.generated.md
# Exclude drafts, but retain a specific file
notes/draft-*.md
!notes/draft-final.md
```

Git ignore syntax is supported, including `*`, `**`, trailing-`/` directory rules and `!` exceptions. If a parent directory is entirely ignored, first unignore it before including its files again. Existing directory-name exclusions and manually removed subdirectories still apply; `!` cannot override them.

Standalone mode rechecks the index before the next search. With desktop auto-watching enabled, creating, modifying, deleting or renaming a rule file rechecks the project, removing newly ignored entries from the index and indexing newly included files. When watching is disabled, use reindexing in File settings. Rules do not delete or hide local files; the Super-SAG file tree still browses them. Only manually removed subdirectories are hidden from the tree.

## Sharing and downloading

The share-code service is not configured; sharing, receiving, and cancellation are unavailable. To access one knowledge base on a local network, see the [web service](/en/docs/remote-access).

## HTTP API

Use `super-sag api start` and `super-sag api stop` to manage the HTTP service. Stopping the API leaves indexing and ordinary CLI searches running. `super-sag api status` shows API and MCP addresses without exposing keys or starting the backend. Add `--json` for JSON output.

Create and show a key with `super-sag api key create --name "Application A"`. List or revoke keys with `super-sag api key list` and `super-sag api key revoke KEY_ID`. Key creation and listing accept `--json`. Export a client configuration with `super-sag api mcp config`; see the [MCP guide](/en/docs/mcp-guide) for address and key options.

Local and LAN applications can call fast or deep search, browse folders and choose multiple directories by their absolute server paths. The CLI's existing search syntax remains unchanged. See the [API overview](/en/docs/api-guide#start-the-service) for setup and [API reference](/en/docs/api) for endpoints.

## Installation locations and upgrades

| Component | User-level location |
| --- | --- |
| npm CLI | npm global installation directory; inspect with `npm prefix -g` |
| CLI managed by desktop or installed with `super-sag install cli` | `~/.local/bin` (`sag.exe` on Windows) |
| Claude Code | `~/.claude/skills/super-sag/SKILL.md` |
| Codex | `~/.agents/skills/super-sag/SKILL.md` |
| OpenCode | `~/.config/opencode/skills/super-sag/SKILL.md` |


Repeating `super-sag install` updates Super-SAG-owned files. Installation records contain checksums, version and the actual CLI installation location. Later PATH-order changes do not change that location, and uninstallation follows the records. If foreign files, user modifications or altered Super-SAG-managed terminal configuration blocks are detected, the installer stops and reports them. Uninstallation removes only verified Super-SAG files and preserves other directory contents.

The command is `super-sag`. When the desktop app first starts after an upgrade, it updates the CLI it manages. If an older CLI at the default location no longer matches its Super-SAG installation checksum, the app backs up that file in the same directory before installing the bundled version. An explicitly uninstalled CLI stays uninstalled. Update an npm-installed CLI through npm.

Windows uses a separate console `sag.exe`, bundled with the application installer. Installing the CLI does not normally require administrator privileges. The Windows packaging entry point is `npm run package:windows`. Available platforms depend on the native executables actually included in a release package.

## Error handling

- Standalone mode: without a desktop service, the local core is used automatically; opening the app is unnecessary.
- Core busy: another process is using the index; retry later.
- Access disabled: enable and save CLI access in CLI settings.
- No indexed content: run `super-sag add` for the current project. The program does not search knowledge bases outside the specified directory instead.
- Index not ready: wait for indexing and inspect file-index errors.
- JEV missing or request failed: inspect configuration with `super-sag config`, or check model settings in the optional desktop app.
- File changed: wait for the watcher to update, then query again.
- Installation conflict: retain existing files and establish their origin before resolving it manually.

After migrating data in the desktop app under [Settings → Data and privacy → Application data location](/en/docs/privacy), CLI versions that support this feature automatically use the same directory. For development and testing, `SAG_DATA_DIR` selects an isolated data directory. CLI and desktop must use the same value to share it; the environment variable takes precedence over the saved location.

## Automatic terminal configuration

- macOS/Linux support zsh, bash, fish and POSIX sh, respecting `ZDOTDIR` and `XDG_CONFIG_HOME`. Repeated installation does not duplicate configuration; uninstalling preserves existing environment settings.
- Windows updates the current user's PATH and broadcasts the environment change, without administrator privileges. Existing terminals keep their old environment; open a new terminal after installation.
- Implementation references: [zsh startup files](https://zsh.sourceforge.io/Doc/Release/Files.html), [Windows environment-change notification](https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-settingchange).

## Harness support

Skill installation is currently provided for Claude Code, Codex and OpenCode.

- [Claude Code Skill](https://code.claude.com/docs/en/skills)
- [Codex Skill](https://learn.chatgpt.com/docs/build-skills)
- [OpenCode Skill](https://opencode.ai/docs/skills/)

For development, builds and code checks, see the [development guide](/en/docs/development).

Search defaults to the current working directory; `--path` overrides it. Semantic search and `-E` / `-F` accept repeated `--exclude` patterns relative to the search root, e.g. `super-sag "aberration" --path "F:/docs" --exclude "archive/**" --exclude "backup/"`. Exclusions apply before candidate retrieval and JEV scoring, without deleting files or indexes. Excluding everything returns no results. Patterns without slashes also match file names. Converted documents in semantic search are matched by their original relative paths and extensions.

For semantic searches with exclusions, each search uses the files allowed when filtering runs; newly added files are included on the next search.

### API key folder scopes

Repeat `--path` to select imported absolute directories, for example `super-sag api key create --name "Project A" --path "/data/project-a" --path "/data/shared"`. Omitting paths or explicitly choosing `--all` preserves full-library access. Existing keys and MCP configurations remain compatible after upgrading.

Use `super-sag api key set-scope KEY_ID --path "/data/project-a"` to change a scope or `super-sag api key set-scope KEY_ID --all` to restore full-library access; one choice is required. Creation, scope changes and listing accept `--json`; listing shows scopes without full secrets. Scope changes apply immediately and cancel that key’s running and queued requests. Export project configurations with `super-sag api mcp config --key-id KEY_ID`. See [Limit folders by project](/en/docs/api-guide#limit-folders-by-project).
