## Environment

Install Node.js 24.x (at least 24.15.0), npm, Rust and the Tauri development dependencies for the target platform; the Windows check workflow is configured for Node.js 24.22.1. Frontend dependencies are pinned in `package-lock.json`; Rust dependencies are pinned in each crate's `Cargo.lock`.

The repository has five Rust build entry points: `protocol/`, `client/`, `core/`, `cli/` and `src-tauri/`. Implement shared logic in `core/` so desktop and CLI do not maintain separate copies.

## Run the desktop app from source

Run from the repository root:

```sh
npm ci
npm run tauri dev
```

The Tauri development command builds the debug CLI first, then starts Vite and the desktop backend. Frontend changes use hot reload; Rust changes require recompiling the backend. Routine UI development does not require repeatedly generating installers.

The desktop development server ignores `.cache/`, `docs-site/`, and `browser-extension/build/`, so documentation and extension builds do not reload the desktop window.

To start only the frontend development server:

```sh
npm run dev
```

The frontend server does not provide Tauri's local file and retrieval interfaces. Use the Tauri development entry point to verify complete desktop workflows.

## Web visual preview (in development)

From the repository root, run `npx vite --host 127.0.0.1 --port 1427 --strictPort`, then open `http://127.0.0.1:1427/tests/visual/` on the same machine. The preview reuses the desktop workspace, shows Super-SAG in the sidebar and About panel, and uses a collapsible sidebar on narrow screens. Open `/tests/visual/?fixture=conversation` to inspect a synthetic conversation and citation; open `/tests/visual/?fixture=search` and enter `示例流程` to inspect a preset search result; open `/tests/visual/?fixture=files` to inspect synthetic folders, the document editor and the location picker for a new document. Conversation search, message editing, streaming responses, tool states and approval dialogs in browser regression also use test data and events; they do not execute real tools. The preview is labeled as synthetic data for interface development. It does not connect to real folders, indexes or models and is not a deployable Web service. Unimplemented writes report an error.

Desktop rebranding is in progress; Windows installation and in-place upgrade still require native acceptance. Do not expose the test preview as a service.

The preview changes some `sag.*` local-storage entries for the same browser origin; use a separate browser profile and a dedicated loopback port. On narrow screens, the sidebar folder menu can be obscured, and the drawer can remain open after navigation. This preview is preliminary work before Windows acceptance. Formal Web comparisons must use the accepted Super-SAG Windows installer as the baseline.

## Build the CLI

```sh
npm run build:cli:dev
npm run build:cli
```

The first command produces a debug CLI; the second produces a release CLI. Development artifacts go in `src-tauri/bin/development/`, and release artifacts go in `src-tauri/bin/`. macOS artifacts go through a signing step.

To install the current build in the user's terminal, run explicitly:

```sh
./src-tauri/bin/sag install cli
super-sag --version
```

The installer checks ownership, checksums and build channel, then validates and replaces each staged executable. If the legacy command cannot be updated, it attempts to restore the new command to its prior state. The development desktop does not automatically update the release CLI, and the development CLI refuses to overwrite a registered release installation. After Rust source changes, rerun `npm run build:cli:dev` so desktop and service have the same build identity, then restart the desktop.

## Build the desktop app

```sh
npm run build
npm run tauri build
```

On Windows:

```powershell
npm.cmd ci
npm.cmd run check
npm.cmd run package:windows
```

An additional local reference project is not required to build an installer. After upgrading Node.js, confirm `node --version` in a new terminal and rerun `npm.cmd ci`.

Use Windows x64, Node.js 24.x (at least 24.15.0), Rust stable with the `x86_64-pc-windows-msvc` target, Microsoft C++ build tools and WebView2. Building also needs network access for dependencies and the NSIS toolchain. Stop and investigate if a command fails. The installer is expected under `src-tauri/target/release/bundle/nsis/`; use the actual build output.

A successful build is not Windows acceptance. Verify fresh installation and the original-app upgrade in an isolated environment first, recording the installer SHA-256, settings and original files. Do not overwrite the only copy of production data. A separate Super-SAG npm package and signed update channel have not been published.

## Code checks

```sh
npm run check
npm test
cargo test --manifest-path protocol/Cargo.toml
cargo test --manifest-path client/Cargo.toml
cargo test --manifest-path core/Cargo.toml
cargo test --manifest-path cli/Cargo.toml
cargo test --manifest-path src-tauri/Cargo.toml --lib
```

If desktop builds or checks require local CLI resources, run `npm run build:cli:dev` first. Use an isolated data directory for manual development checks to avoid affecting the everyday knowledge base:

```sh
SAG_DATA_DIR=/path/to/dev-data npm run tauri dev
SAG_DATA_DIR=/path/to/dev-data ./src-tauri/bin/development/sag service status
```

Set the same `SAG_DATA_DIR` when desktop and CLI should share development data. The service starts on demand after it exits; quitting the desktop does not stop it. Run `super-sag service stop` after testing when needed. Features that need a model service use credentials configured by the developer. Indexing and local matching do not require API keys.

## Documentation and repository boundaries

`docs/` contains the current architecture, development guides, interface documentation and clearly identified design plans. Update the relevant document when implementation changes, rather than adding conflicting historical descriptions.

Keep development artifacts, temporary output, logs, screenshots and local data out of the documentation directory. Credentials and user knowledge bases must not enter release packages. Keep automated tests and required fixtures in their respective test directories.

## Web Clipper extension

Run `npm run build:clipper` for Chrome / Edge packages in `src-tauri/clipper/`. On macOS with full Xcode, run `npm run build:clipper:safari` for the local Safari test app in `browser-extension/build/`. Test builds use the separate `com.sag.webclipper.development` identifier so they do not interfere with the installed release.

To prepare the production Safari app, run `node browser-extension/build.mjs --safari --release`, then sign and notarize both the app and its DMG. macOS desktop builds use the notarized installer at `src-tauri/clipper/sag-web-clipper-safari.dmg`, or the path supplied through `SAG_CLIPPER_SAFARI_DMG`, and stop if verification fails. Desktop builds do not overwrite release installers with unsigned test packages.
