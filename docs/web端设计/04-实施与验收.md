# 04 实施顺序与验收矩阵

## 阶段顺序与门槛

| 阶段 | 交付 | 进入后续阶段的验收 |
| --- | --- | --- |
| 0 基线 | 固定参考源码、原版 Windows 包、Super-SAG 标识及需求。 | 摘要和引用可复核；明确哪些 Windows 状态仍待实机确认。 |
| 1 Windows 桌面 | 品牌统一、可打包、覆盖升级并保留原版数据，桌面继续本地免登录。 | 真实 Windows 生成/安装新包，隔离环境验证全新安装和原版数据升级，正常、极值、边界、失败及原功能回归通过；冻结安装包和对照资料。用户本机反馈前标记待验收。 |
| 2 Web 视觉 | 在阶段 1 通过并冻结基准后，优先复用桌面组件，完整还原 Windows 各页面和交互状态。 | 对已验收的 Super-SAG Windows 安装版，在相同数据、视口、缩放、主题和语言下以真实 Chromium 逐屏对照；替身仅用于测试，差异须记录并与用户确认。 |
| 3 Web 业务 | 授权服务器目录、原文件、格式、索引、文件操作、搜索、问答、引用及设置与桌面逐项对齐，完成 Linux 启动。 | 使用真实服务、真实文件和索引，通过正常、极值、边界、失败及真实浏览器验收；对比已验收 Windows 同输入结果。 |
| 4 多租户 | 在等效业务外增加身份、成员、租户、知识库和个人数据隔离。 | 产品入口真实创建 A/B 租户、成员及授权，真实目录索引、检索、问答和跨租户拒绝；浏览器及服务端正常、极值、边界、失败、越权与撤权回归通过。 |
| 5 部署 | 按 `app.sh` 操作，监听 `0.0.0.0:8167`，持久化、升级、备份恢复及部署文档。 | 干净 Linux 环境验证启动、重启、恢复和访问；Web 安全及 Windows 本地回归闭环。 |

当前第一优先级是 Windows 品牌、构建和真实安装/覆盖升级验收。Windows 基准冻结前不把 Web 工作作为正式实施主线；已有 Web 测试预览保留为预研，不视为阶段 2 通过，Windows 完成后须逐项重做正式对照。之后先完成 Web 样式与交互，再逐项接通业务；多租户不抢在业务基线之前。任何阶段通过只表示该阶段记录的范围通过。

## 证据规则

- 每个切片记录 Git 基线、改动范围、真实/模拟环境、测试输入、预期、实际、正常/极值/边界/错误结果、截图、未通过项和风险。
- Web 真实浏览器运行实际页面；视觉测试替身必须单独标明，不能代替真实文件、模型、索引和权限验收。涉及共享代码时还须真实 Windows 桌面回归；未获反馈的切片标记待 Windows 验收。Windows 实机必须由真实安装包执行，不能由 Chromium、Vitest 或 Linux 模拟代替。
- 测试脚本运行前须验证参考提交及逐文件摘要，隔离测试浏览器存储；逐屏保留可比较截图及差异。所选节点的矩形、字体族或前景色检查不是全页面像素一致性证明。
- 隔离演示数据不含个人信息、业务文档或凭据；任何删除/覆盖试验只能操作专为测试准备的数据。正式用户数据不作为测试夹具。
- 每次更新用户文档时同步中文、英文和受影响截图，执行 `npm --prefix docs-site run build`，检查链接和搜索。未经当次指令不发布。
